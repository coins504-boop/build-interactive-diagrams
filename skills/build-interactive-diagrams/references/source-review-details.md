# Conditional source-review detail

Read the relevant gate when the modeled source has the corresponding interaction. The concise obligations live in [source-modeling.md](source-modeling.md#mandatory-source-review-gates); this expands them, not the requested scope. Search: activation/options, reconstruction/ownership, error-origin, independent events, callbacks, intermediate state, adversarial controls.


Before freezing a detailed source reconstruction, and after a semantic repair, record the applicable checks below in the existing behavior map/review. Keep source evidence, source-valid probe inputs, expected/observed effects and model IDs together. Mark a genuinely inapplicable gate with its reason; an untested applicable gate remains an explicit limitation, not a pass. These are author/reviewer obligations, not automatic source checks.

1. **Activation and exact predicates.** For each consequential injected observation, record the actual callsite, active variant, allowed results and ordered guard. Pair an inactive/no-op path carrying a stale failure with an active fallible path. Distinguish absent/default/custom implementations and the source's real null/false/truthy sentinel states; a broad description such as “initial only” is not equivalent to an exact predicate. When context/owner selection changes, verify which settings are replaced and which are deliberately retained.

   Trace consequential options across callers: key presence, default/pop/merge, forwarded null/false/true, downstream guards and fallback effects. A false value may disable only one operation while still scheduling work. Use distinguishing presence/value cases; checking only the final boolean guard can miss an active side path. At a recursive call, retry, replacement or actor handoff, separate the caller-supplied keys, current resolved values, explicitly forwarded fields and the successor callee’s defaults. Omission is not an explicit false value or permission to inherit the effective value. Name whose configuration each re-entered API reads; separate actors need separate settings or a visible bounded assumption, even when they call the same API.
2. **Entry and ownership.** State per-entry relationships and valid histories beyond scalar input domains. Classify modeled state as shared/pre-existing, per-invocation derived, or an injected observation. Initialize only what this invocation owns, after any no-work gate that precedes ownership acquisition. Seed a no-op/duplicate entry with meaningful non-default shared state and assert preservation plus absence of new calls/cleanup; contrast a fresh entry with stale per-run output flags. Reopening a simulation does not justify resetting another source operation's state. Unsupported histories must be rejected or visibly excluded, not called source errors.

   At reconstruction, distinguish a staged successor from an entered one, reuse from fresh allocation, and per-instance flags from retained parent handles/shared data. Reset only the new owner’s fields; copy only source-forwarded fields. Assert actual context at the reconstruction checkpoint and any earlier old-owner effect, including fields deliberately unchanged. Contrast omitted and explicit options, an old non-default instance flag and disagreeing actor settings. Include a broken model whose later actions repair its terminal state: a terminal-only assertion or a separately recorded expected value must not conceal the wrong live checkpoint.

   If the interface accepts an unsupported history, reject it at an explicit admission step or restrict that entry/editing surface. Prose exclusion alone must not allow a misleading success playback. Probe completed prior work, active resources and stale outputs against the declared entry relationships; distinguish model-scope rejection from a product error.
3. **Caller continuation and failure phase.** Follow a callee's return to its actual caller. Distinguish a returned error value, thrown exception, logged/ignored result and callback failure; do not propagate an error merely because the callee can produce one. Compare callers/phases with different handling, transaction ownership or cleanup. Separate repeated observations when later calls can differ; do not assume clock observations are monotonic. Register deferred/finally effects only after their source registration point, then preserve them on covered exits. Probe pre-effect failure and post-effect failure; assert retained external/durable effects separately from the caller's rollback or response.

   **Error-origin and owner propagation.** For each relevant throwing/callback site, map the guard and actual receiving owner, its backward cancellation/cleanup effects, and subsequent forward error delivery. Do not route all failures to a shared final owner merely because the final error/outcome agrees. Contrast failures owned by an intermediate stage with failures owned by the final stage when both exist; their cleanup entry and order may differ. Keep this small origin/owner matrix beside the existing source map, including error payload and retained effects.

   For each asynchronous side path, name who schedules/registers, cancels, awaits and observes completion. Unregistered work is not another registry entry; main-task cleanup does not establish its termination. Preserve scheduled/outcome-unobserved where appropriate. If stopping is in scope, separate user stop, network failure/disconnect and local playback cancel; trace partial-output retention, incomplete state, notification/save/cleanup order and when a request becomes an observed stop. Do not infer one route's guarantees from another.
   **Independent events across an awaited call.** Separate an event's source owner and reachability window from the awaited operation's eventual result. If the chosen source-valid history includes an edit/message/timer event after dispatch but before settlement, apply its state and notification effects at that boundary on both success and later-failure paths; a failed await cannot erase an already observed independent event unless the source explicitly does so. Preserve the captured in-flight payload separately from subsequently changed live state. A single-active-node player may illustrate this legal order but does not execute concurrency.

   State whether an input requests an event only if a named phase is reached, or asserts that the event already occurred. A hypothetical event in an unreached phase is not an observed event: contrast validation/cancellation before dispatch with an event during the pending call followed by rejection, and with a later observation failure. For an asserted observed history, require its actual call/registration prerequisites or reject the unsupported combination at the existing admission boundary. Derive these distinctions from source; do not inject every event at entry, condition it on all-success, or treat every event flag as an inactive stale failure.
4. **Observable state over time.** Assert claimed outputs and lifecycle state at consequential intermediate nodes as well as the terminal: acquisition/staging, dispatch, effect completion, observation and cleanup. Entry actions run during `start`, and target actions before each `step` result. Use those actual snapshots; trace events contain IDs, not historical context. Check at least one pending/active state that later clears, call counts and the absence of premature cleanup. A terminal-only pass can hide an incorrect UI for the whole journey. Mark attempted, confirmed and unknown effects distinctly.

   A graph that explicitly claims internal owner state must prove that state at the relevant closure, upstream cleanup and error-forwarding checkpoints, even when an external-event projection cannot observe it. Pair source-valid origins with opposite cleanup ordering where the source requires it. Include a wrong-order control whose complete final context and external events still agree; neither is proof of the internal phase claims. If internal state is intentionally abstracted, remove or qualify those claims rather than inferring them from external traces.

   **Callback observation boundaries.** Before combining state writes and later effects into one node, trace the intervening call chain through result recomputation, equality/property filters, registered wrappers and actual callback execution. Record which values a callback receives as a captured payload and which it reads from live state. If a source-admitted inline callback can observe the state before the next effect, preserve that boundary even when the combined node reaches the right terminal state. Split the actions at that boundary and assert the callback-visible values, not just event IDs or a final status. Name cancellation intent, effect invocation and confirmed effect separately when the source distinguishes them.

   Derive delivery timing from the actual wrapper/scheduler and active configuration; a name such as “batch” proves neither inline nor deferred execution. Contrast an eligible direct callback, a filtered/absent callback and a queued wrapper where those routes exist. Recomputed state need not mean a listener ran, and a scheduled wrapper need not mean its callback ran. For a later callback, distinguish its captured payload from live values read when it executes; do not project one framework/default scheduler onto every route. Record callback exceptions/reentrancy as source-specific continuations under gate 3, or explicitly bound the fixture to nonthrowing, non-reentrant callbacks. Do not invent their behavior to make an ordering probe pass.

   For each independently occurring event in the selected history, assert its live state, emitted notification count and actual listener/consumer observations at the event checkpoint and after later failure. Emission and delivery may differ; derive their relationship from the source and active listener/scheduler rather than counting only the first event or assuming every emitted event is observed.

   Bind attempt/sent/confirmed counters to actual call/return/observation points. A composite phase with an earlier fallible operation cannot count a later call on entry: split the phase or name the count as phase entry only. Pair an earlier failure with a stale later failure and assert the later attempt remains zero.
5. **Adversarial contrasts after repair.** Derive neighboring combinations from the source map, including an earlier return plus a later stale failure and a caller/variant differing from the original reproduction. Recheck the repaired family, not just named author scenes. Use small distinguishing pairs/boundaries rather than a blind Cartesian product. Probe expectations must exclude the changed input itself when measuring behavior. The bundled [semantic-probes.test.js](../tests/semantic-probes.test.js) demonstrates twelve small patterns and broken-model negative controls using the existing engine; adapt assertions beside each project, without a new schema, parser or project-specific runtime patch.
6. **Review the review.** Preserve the source-first inventory, then compare source→model and model→source. Independent review first discovers responsibilities/defaults and expectations from the original request and pinned source without the model/author map; preserve that result before comparison and add discoveries to the coverage record. For each material disagreement reread the exact guard, caller and callee, verify the reproduction satisfies declared entry/scope assumptions, and try the nearest counterexample to the proposed repair. Independent reviewers can overgeneralize too. Record corrections to earlier conclusions explicitly; do not silently replace a frozen reference. Resolve the mismatch or narrow the claim with a visible reason; narrowing a claim does not close unmet requested coverage without the actual work or user-approved scope change.

Keep entry constraints beside each selectable entry. Input domains constrain merged entry values, not every later output state or arbitrary history; a terminal may intentionally mark an output unknown outside its entry enum. A source-isolated snapshot is not a callable composition API. If the host advertises editable contexts, test edits against those constraints or restrict that promise; do not invent source exceptions for explicitly out-of-scope inputs. A finishing-task entry may require active >= 1 while a valid post-limit-decrease state has active > limit.

Use local `Simulation.start/step/inspect` or the existing `scripts/run.js` commands for probes, without executing upstream code. Store assertion code and actual results beside the project so others can replay them; no new spec acceptance syntax is needed. Run structural/evidence checks, these source-derived probes, authored acceptance and visual/human-reading checks as separate evidence layers. No layer certifies complete source equivalence.
