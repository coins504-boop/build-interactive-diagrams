# Reconstruction pipeline integrity details

For pipeline troubleshooting, integrity review or maintenance. Ordinary builds use the command and failure rules in [repository-reconstruction.md](repository-reconstruction.md#check-project-build). No new user steps are introduced here.

Start the wrapper with a trusted Python 3.10+ interpreter using `python3 -I -S` as shown. This isolates the first interpreter from user/environment Python startup hooks before the wrapper loads. The wrapper separately uses isolated Python child flags and a per-process environment allowlist, dropping Python/Node preload options, dynamic-loader hooks and other inherited overrides; Node must be a trusted 18+ executable resolved through PATH. This does not undo startup code already executed by an unisolated parent and is not a host security sandbox or protection against substituted executables or modified toolchain code. No system settings are changed. The CLI is the supported entry point; direct `build_run`/`verify_run` imports assume an already trusted, isolated caller and provide no retroactive parent-startup protection.

The entire `--out` run directory must not exist, even if empty or a dangling symlink. A failed run retains available stage output and normally `FAILURE.json`, has no success receipt, and must not be resumed. Abrupt interruption may prevent writing a failure record: absence of a valid final success receipt always means incomplete. Prepared bytes are checked before each following child stage; interstage drift stops the chain before launching that stage. Fix the cause and select a fresh run directory. In particular, `ERROR: Output exists` is failure, never permission to build an older prepared spec. Never prepare from previously prepared output. The original low-level commands remain available with unchanged behavior; independent success from a later command does not establish a successful chain.

The run contains an exact raw `source-spec.json` snapshot, `prepared-spec.json`, captured stage records, `workspace/` and a final `ARTIFACT_RECEIPT.json`. The construction folder and ZIP also retain the original raw bytes and their provenance. The final inspection checks the actual prepared spec against the current raw spec's exact permitted projection, then checks workspace spec, native cells and embedded model, blueprint, acceptance artifact, copied runtime assets and ZIP member bytes. JSON comparisons distinguish Boolean, number, null, string, object and array; object key order is irrelevant and equivalent numeric forms such as `1` and `1.0` remain the same JSON number. Exact file hashes separately bind lexical bytes. Duplicate JSON object keys are rejected at this wrapper boundary. The required construction artifact set is fixed, and `NODE_INDEX.md` must reproduce every ordered node ID, label, parent, role, docs value and action from the prepared model, even when a stale/missing index has a self-consistent manifest and ZIP. It retains all authored node/edge/claim/boundary/coverage mappings, including summaries and nonexecuting relationships. Equal runtime traces or matching counts are insufficient. Raw/prepared byte equality is not required: generated citations and reports, removal of the five reserved derived evidence fields, and explicitly requested overview presentation are legitimate preparation changes. Ordinary authored metadata remains intact; the preserved raw bytes are provenance, not authoritative verification claims.

`verify` requires the current original source-model file and checks its byte digest, successful stage input hashes, artifact file set and byte hashes, and the model projection again using the producing skill. It does not rerun upstream source verification or establish semantic completeness. The receipt is an unsigned local integrity record, not a tamper-proof attestation or author-independent review. No source-truth or visual-inspection success is manufactured. Keep the whole run together and verify immediately before delivery. Changed source, files, native layout exports, stage records or toolchain invalidate this receipt; start a new build rather than relabeling the previous receipt as current. Source-first and browser review remain separate required gates.


Preparation projects resolved claims, source pins, adjacent relationships and boundaries into the reserved docs.sourceEvidence. Full source model/check reports remain in prepared spec, blueprint and native export. Evidence and technical simulation context are progressively disclosed.

Checks cover reference integrity, typed edges, local paths, line bounds, file hashes and local Git blob equality. Metadata-only runs do not verify source. Git-less cited-byte checks leave revisions unverified; explicit local snapshots verify every manifest file without claiming whole-workspace or Git coverage. Paths stay within selected roots. Structural containment/connectivity and relationshipGraph do not establish execution reachability; evidenceStats counts claim-referenced citations, not facts proved.
